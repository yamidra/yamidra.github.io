De la teoría a la práctica: walkthrough en acción

Objetivo general:

Demostrar la capacidad de aplicar conocimientos teóricos de seguridad informática en un entorno práctico, mediante la realización de un walkthrough detallado y la explicación de las técnicas y metodologías utilizadas para vulnerar una máquina virtual.

Configurar un entorno de virtualización

Para configurar un entorno de virtualización aislado tenemos que configurar los adaptadores red de la maquina vulnerable (Snake oíl) y de la maquina en la cual vamos a hacer las pruebas de Pentesting que en este caso es una maquina con Kali Linux

En VirtualBox realizaremos el siguiente proceso en cada una de las máquinas virtuales, clic derecho a la maquina a configurar, dar clic al apartado red, del lado derecho encontraremos la opción conectada a, aquí seleccionamos la opción: adaptador solo anfitrión, esta opción nos genera una red interna en la cual solo la maquina Snake oíl y Kali Linux estarían conectadas sin acceso a internet. Una vez realizado este proceso encendemos las maquinas.

Enumerar los servicios y aplicaciones en ejecución

En Kali Linux empezamos identificando la dirección Ip de nuestra maquina abriendo la terminal y ejecutando el comando ifconfig.

Ahora necesitamos encontrar la dirección de la maquina Snake oíl para esto usamos el comando netdiscover este trabaja enviando petición brodcast la cual responden todos los hosts menos el que la envía dentro de una red con su Mac y dirección Ip asociada, en sus opciones tendremos que ingresar la interfaz que estamos usando y el rango de direcciones que estamos buscando de la siguiente forma.

sudo netdiscover -i eth0 -r 192.168.56.00/24

Aquí podemos ver tres direcciones Ip descartando la primera que pertenece al adaptador de red interno de VirtualBox y la segunda al servidor DHCP de VirtualBox. Descubrimos que la dirección: 192.168.56.103 pertenece a la maquina Snake oíl.

Una vez que tenemos la dirección tendremos que enumerar los servicios activos sobre esta Ip para eso usamos el comando nmap que nos ayudara escaneando todos los puertos abiertos, así como el servicio y la versión de este de la siguiente manera.

sudo nmap -p- -sV 192.168.56.103

Al analizar la información obtenida podemos ver que está abierto el servicio shh y los puertos 80 y 8080 los cuales me indican que se está ejecutando un servidor web nginx.

Vulnerabilidades conocidas asociadas con los servicios

Al ingresar al servidor podemos ver páginas web simples sin protección https lo cual nos permitirá ver las peticiones y respuestas del servidor web ya que no están encriptadas

Seleccionar y adaptar los exploids

Haremos uso de la de la herramienta dirb la cual escanea directorios ocultos dentro del servidor comparando sus nombres con una lista directorios comunes en un servidor web de la siguiente manera dirb

http://192.168.56.103

Al ejecutar el escaneo en el puerto 80 no arroja ningún directorio por lo cual este puerto queda descartado ejecutamos un escaneo por el puerto 8080 de la siguiente manera

http://192.168.56.103:8080

Gracias a esta Herramienta logramos encontrar directorios con nombres interesantes como login, registration, run, secret, test, users.

Usamos esta información para nuevamente navegar por estos directorios encontrándonos con respuestas propias de un sitio web en construcción y con funcionalidades de api por lo cual podremos interactuar con esta.

Ya que no se esta usando el protocolo https, necesitaremos interceptar, analizar y modificar el tráfico entre un navegador y un servidor para detectar vulnerabilidades en esta aplicación web, por esto usaremos Burp Suite.

Analizaremos las peticiones y respuesta de cada sección gracias al uso del Proxy de Burb Suite, empezaremos por secret ya que por su nombre podría contener algo de suma importancia.

El respuesta a esta petición como podemos ver en la linea 4 Content-Type: application/json nos indica la forma en que se esta interpretando los datos, por lo cual si queremos interactuar con ella tendremos que darle datos en este mismo formato aquí el mensaje nos arroja un Error de Servidor interno, este mensaje nos puede indicar que algo anda mal o que necesita algún dato para que funcione correctamente como no lo sabemos lo dejaremos por el momento.

La siguiente sección de interés es la de users ya que puede contener el nombre de usuario y contraseña del administrador

La respuesta de esta petición en el formato antes mencionado nos deja ver información relevante como un nombre de usuario “patrick” y una contraseña que al parecer esta cifrada.

Ya que tenemos un nombre de usuario podríamos interactuar con la sección login.

Burp Suite nos permite modificar las peticiones enviando el código de esta a la sección Repeater por lo cual enviaremos cada una de estas. La repuesta a esta peticion nos esta enviando el mensaje: El método no esta permitido para la URL solicitada.

Cambiamos el método a POST dando clic derecho sobre el contenido de la petición, clic en la opción Change request method, clic a enviar, y ahora podemos ver en la respuesta el mensaje que necesitamos un nombre de usuario por lo cual probamos con el que conocemos “patrick”.

Damos el formato adecuado a nuestra petición agregando la linea 4 Content-Type: application/json de la respuesta al final de la petición abrimos y cerramos llaves y copiamos el formato del response indicando el nombre de usuario: “username”:“patrick”, la aplicación nos responde que el campo de contraseña no puede ir en blanco.

Ingresamos un valor de contraseña, nuevamente en el formato que esta solicitando contraseña: “password”:“patrick”, podemos ver el comportamiento de la api en busca de alguna vulnerabilidad, sin embargo solo obtenemos el mensaje que las credenciales no son correctas.

Ya que probamos que el usuario “patrick” que encontramos en la sección users hasta hora no sirve de mucho, probemos la sección registration la cual nos podría ayudar a crear un usuario.

La respuesta a esta petición nos está enviando el mensaje: Error en el método.

Al cambiar de método ahora nos pide al igual que el login un nombre de usuario y por lo tanto una contraseña y le daremos el formato solicitado. “username”:“admin”,“password”:“admin”.

Al enviar este petición que el proceso esta hecho sin pedir un tipo de usuario o permiso para crearlo y nos envía un access_token el cuales es JWT (JSON Web Tokens) este es un formato estandarizado donde se envía información del usuario como parte de autentificación y manejo de sesiones este se compone de 3 secciones el header que es la parte seleccionada de la img-19 nos da información que es un JWT que se encripto en HS256. El payload que es la parte de la img-20 la cual nos da algunos datos del usuario sin embargo ninguno de estos datos incluye alguna información de relevancia y por ultimo una firma criptográfica la cual se podría descifrar para firmar nuestros propios JWT pero analizando las paginas del servidor web no interactúan con JWT externos solo da este como una identificación de sesión o Cookie que nos puede servir mas adelante.

Vulnerabilidades encontradas después del pentesting

  • La página no usa https por lo cual las peticiones y repuestas pudieron ser observadas y manipuladas.
  • Usar nombres comunes para directorios web permite identificar que hace cada sección.
  • Manejo inapropiado de errores estos nos dan información de lo que necesita para que el api nos responda, aunque el usuario no sea autorizado.
  • Creación de usuarios no establece ningún control en lo que puede y no puede hacer un usuario.
  • Acceso a contraseñas en el servidor web estas claves no deberían estar dentro de los archivos del sitio web.
  • Acceso a contraseñas solo con un token de sesión sin validar su uso o el usuario que la creo.
  • Permitir correr comandos del sistema y mostrar su ejecución dentro del sitio web.
  • Reutilización de credenciales podemos encontrar credenciales de usuario y contraseñas redundantes que nos permitieron tomar acceso al sistema.

Conclusiones

Las pruebas de pentesting son primordiales para la puesta en servicio de un sitio web seguro, mitigando vulnerabilidades en las aplicaciones de desarrollo, la organización de nuestras credenciales y el tipo de acceso que le permitimos al usuario final y a cualquier usuario que de manera mal intencionada quiera hacerse de información relevante o apropiarse de nuestro sistema.
